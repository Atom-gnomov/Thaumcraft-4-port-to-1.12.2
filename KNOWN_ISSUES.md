# Известные проблемы

Список открытых багов/недоделок порта Thaumcraft 4 → 1.12.2 на текущий момент.
Закрытые пункты переносятся в `CHANGELOG.md` при исправлении, отсюда удаляются.

## Бо́льшую часть контента TT нельзя получить в выживании

**Severity: блокирует модуль.** Найдено аудитом 2026-07-28, после 1.1.23.0.
**Частично закрыто:** вкладка `TT_CATEGORY` и ветка фокусов — в 1.1.25.0,
ствол `DARK_QUARTZ` со всем поддеревом — в 1.1.26.0. Остальное — ниже.

**Отдельная ловушка, найденная в 1.1.26.0.** Обёртки рецептов оригинала берут
`(ключ_карты, гейт_исследования)`, и у части объектов это **разные** строки:
`MAGNET`/`MAGNETS`, `MOB_MAGNET`/`MAGNETS`, `INTERFACE1`/`INTERFACE`,
`RELAY`/`LEVITATOR`, `SUMMON0`/`SUMMON`, `ICHOR_AXE`|`PICK`|`SHOVEL`|`SWORD` →
`ICHOR_TOOLS`, `ICHORCLOTH_HELM`|`CHEST`|`LEGS`|`BOOTS` → `ICHORCLOTH_ARMOR`.
Взять первый аргумент за гейт — значит повесить рецепт на ключ, которого нет
ни в одной записи. Так и было с блоком призыва (гейт `SUMMON0`), починено.
**Ихориевые инструменты ещё не сверены** — при их исследованиях проверить, что
все четыре гейтятся на `ICHOR_TOOLS`, а не каждый на своё имя.

`ShapedArcaneRecipe.matches` и `InfusionRecipe.matches` начинаются с проверки

```java
if (this.research.length() > 0 && !ThaumcraftApiHelper.isResearchComplete(player.getName(), this.research))
    return false;
```

а `isResearchComplete` возвращает `false` для ключа, которого нет ни в одной
записи Таумономикона. Ветка исследований Thaumic Tinkerer не портирована, то
есть **таких записей нет ни для одного ключа TT**.

Гейтом закрыт 51 рецепт `ConfigTinkerer`. После 1.1.26.0 достижимы 27 из них.
Оставшиеся **24 рецепта висят на 21 ключе оригинала**, для которых записи
Таумономикона нет, то есть эти рецепты не сработают никогда:

```
BLOCK_TALISMAN  CAT_AMULET  ENCHANTER  FUNNEL  GAS_REMOVER
ICHORCLOTH_ARMOR (x4)  ICHORCLOTH_BOOTS_GEM  ICHORCLOTH_CHEST_GEM
ICHORCLOTH_HELM_GEM  ICHORCLOTH_LEGS_GEM  ICHOR_POUCH  INFUSED_INKWELL
PLACEMENT_MIRROR  POTIONS0  POTIONS1  POTIONS2  POTIONS3  PROTOCLAY
REPAIRER  REVEALING_HELM  XP_TALISMAN
```

Половина из них — ярус KAMI (`ICHOR*`, `BLOCK_TALISMAN`, `PROTOCLAY`,
`PLACEMENT_MIRROR`, `XP_TALISMAN`, `CAT_AMULET`); он закрывается вместе со
своим гейтом, см. следующий пункт.

Пересчитать список: `ConfigTinkerer` даёт ключи первым аргументом
`addArcaneCraftingRecipe`/`addInfusionCraftingRecipe`, наличие записи —
`new TinkererResearchItem("KEY"` в `ConfigResearchTinkerer` либо
`new ResearchItem("KEY"` в остальных `ConfigResearch*`.

Верстачные рецепты (`ShapedOreRecipe`) исследованиями не гейтятся и работают:
вся цепочка закоптившегося кварца, том обмена, прессовка аспектов души,
перезаправка письменных принадлежностей.

### Как так вышло

До 1.1.6.0 рецепты висели на *существующих* исследованиях TC4 (`FOCUSFIRE`,
`GRATE`, `MIRROR`) — то есть работали, но гейт был выдуман. Аудит 1.1.5.0
справедливо назвал это выдумкой, и 1.1.6.0–1.1.10.0 заменили ключи на
оригинальные. Значения рецептов от этого стали верными, а гейт — висячим:
перенесли половину пары «рецепт + исследование».

**Урок для правила «ничего не выдумывать»:** заменяя выдуманное значение на
оригинальное, надо проверять, что всё, на что оно ссылается, тоже существует.
Ссылка на несуществующее — такой же дефект, как выдуманное число, только тише.

### Что делать

Единственное правильное решение — **портировать ветку исследований TT**. Все
записи выписаны в [`TT_OBJECT_REFERENCE.md`](TT_OBJECT_REFERENCE.md): у каждого
объекта есть `getResearchItem()` с ключом, аспектами, координатами на карте,
родителями и страницами. Это последняя большая недостающая система модуля, и
теперь понятно, что без неё модуля фактически нет.

Промежуточных костылей не ставить: временно вернуть чужие ключи TC4 — значит
вернуться к выдуманному гейту, который уже один раз пришлось убирать.

Порядок работы задан в 1.1.25.0 и повторяется для каждой следующей группы:

1. Взять `getResearchItem()` в оригинале (`tt-original-1.7.10`), не в пересказе.
2. Дописать группу в `ConfigResearchTinkerer` через `TinkererResearchItem`.
3. Скопировать `ttresearch.name/lore/page.*` для её ключей из оригинальных
   `en_US.lang` и `ru_RU.lang` дословно — свои формулировки не сочинять.
4. Прикрепить страницы рецептов строгими `ConfigResearch.recipeArcane/
   recipeInfusion` — промах ключа должен падать, а не молча давать текст.
5. Расширить `TinkererResearchStaticGuardTest`: и запись, и пару «гейт ↔
   запись» (`everyFocusRecipeGateHasAnEntry`).

Родители ведут на записи соседних групп, поэтому порядок важен. Дерево
оригинала (`setParents` в `getResearchItem()`, в кавычках — ключи самого TC4):

```
"FOCUSEXCAVATION" → FOCUS_SMELT → FOCUS_FLIGHT → FOCUS_TELEKINESIS      готово
                                              → FOCUS_DISLOCATION      готово
                                → FOCUS_DEFLECT → FOCUS_HEAL           готово
                                                → FOCUS_ENDER_CHEST    готово
DARK_QUARTZ → INTERFACE → MAGNETS → ANIMATION_TABLET → REMOTE_PLACER   ← нет
            │           │        └→ LEVITATOR                          готово
            │           └→ DISLOCATOR                                  готово
            └→ CLEANSING_TALISMAN → BLOOD_SWORD → SUMMON               готово
                                  └→ PLATFORM                          готово
"NITOR" → GASEOUS_LIGHT → GASEOUS_SHADOW
                        └→ BRIGHT_NITOR → FIRE_{AER,AQUA,IGNIS,ORDO,
                                       │    PERDITIO,TERRA} → POTIONS
                                       └→ FUNNEL → REPAIRER
SPELL_CLOTH → ENCHANTER → 14 записей ENCHANT_* (см. TT_OBJECT_REFERENCE.md)
            └→ XP_TALISMAN (второй родитель — "JARBRAIN")
"GOGGLES" → REVEALING_HELM
PERIPHERALS → ASPECT_ANALYZER, GOLEMCONNECTOR
```

Следующие корни — `GASEOUS_LIGHT` и `SPELL_CLOTH`: без них ни одно из их
поддеревьев не встанет. Обратите внимание, что сами эти корни в списке висячих
ключей выше не значатся — рецептов на них нет, они существуют только как узлы
дерева, и портировать их всё равно нужно.

Два замечания по именам, чтобы не повторять чужие ошибки:

- **Ключ ≠ имя класса.** `LibResearch.KEY_MOBILIZER` — это строка
  `"LEVITATOR"`. Ключ всегда брать из `LibResearch`, а не из названия класса.
- **`REMOTE_PLACER` пока пропущен**: сам объект (`BlockRPlacer`) в порт не
  перенесён, а запись без рецепта упала бы на строгом lookup. Его исследование
  ставить одновременно с блоком.

## KAMI лежит в общем наборе предметов, без своего гейта

**Severity: ломает прогрессию.** Найдено 2026-07-28 при проверке вопроса
«ками включён в обычный набор айтемов?».

В порту содержимое KAMI регистрируется и попадает во вкладку так же, как
обычные предметы: `ItemIchorPick` и соседи ставят
`setCreativeTab(CreativeTabThaumcraft.tabThaumcraft)`, а условия регистрации
нет вовсе — `grep enableKami` по `mod/src/main/java` не находит ничего.

В оригинале это отдельный ярус с тремя разными замками:

1. **Конфиг.** `ConfigHandler.enableKami` (по умолчанию `true`, но опция есть),
   и `ItemKamiBase.shouldRegister()`/`shouldDisplayInTab()` возвращают именно
   его — при выключенном KAMI предметы не регистрируются совсем.
2. **Исследования.** `KamiResearchItem` всегда `setConcealed()`, а в
   `setPages` он собирает в `parentsHidden` **все** исследования всех
   категорий, кроме потерянных, виртуальных, других KAMI и чёрного списка
   (`MINILITH`, плюс всё, что кончается на `KAMI`). То есть ни одна запись
   KAMI не откроется, пока не пройдена практически вся книга. Это и есть
   настоящий гейт яруса, и у нас его нет.
3. **Подпись.** Лор у них с префиксом `ttresearch.prefix.kami` = `[TTKami] `
   вместо `[TT] ` — видно, что предмет из позднего яруса.

Чинится вместе с веткой исследований: нужен `TinkererKamiResearchItem`
(подкласс `TinkererResearchItem` с этим `setPages` и своим `getPrefix`), опция
конфига и гейт регистрации. До тех пор ярус доступен с первой минуты.

## Известные архитектурные ограничения (не баги, а осознанные компромиссы)

- Просканированные предметы игрока хранятся как необратимый хэш
  (`ScanManager.generateItemHash`) — обратный поиск `ItemStack` по хэшу работает
  только через фоновый кэш `MappingThread`/`GuiResearchRecipe.cache`, который
  строится один раз за сессию и может не успеть заполниться в первые секунды
  после захода в мир.
