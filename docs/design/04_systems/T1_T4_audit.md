Шесть независимых аудиторов прошли по срезам T1, T2, T3, T4, по

## А-1 (БЛОКЕР, порт). Скидка на вис делилась на 100 дважды — это моя ошибка

**Суть.** В порте 1.2.8.2 я «починил» `getConsumptionModifier`, добавив
деление на 100. Оно было лишним: движок уже делит.

**Доказательство.**

```java
// WandManager.getTotalVisDiscount — так было ВСЕГДА, с базового импорта:
return (float) total / 100.0F;      // сумма процентов → доля

// ItemWandCasting.getConsumptionModifier в 1.2.8.2 (моя правка):
discount -= WandManager.getTotalVisDiscount(player, aspect) / 100.0F;  // ← второе деление
```

`git log -S "return (float) total / 100.0F"` показывает, что строка в
`WandManager` пришла из коммита `5b40dff` (базовый порт), а мой коммит
`97bdcc2` её не трогал — то есть деление стало двойным.

**Последствие.** Гогглы (5 %) давали 0.0005 вместо 0.05 — скидки нет ни
у одного предмета; штраф нашей брони (отрицательные значения) тоже не
работал. Тихо, без единого сообщения в лог: каст просто стоит полную цену.

**Исправлено** в порте 1.2.8.3: деление убрано, у строки оставлен
комментарий-предупреждение. Канон `02_world_model.md` §6 переписан — теперь
там сказано, что перевод процентов в долю делает сам движок.

## А-2 (важно, T2). Домна тратит воздух **за тик**, а не за операцию

**Суть.** Карточка закалённого таумия просила `fluid = 2` «за цикл».
Такого понятия у печи нет.

**Доказательство** (`TileEntityBlastFurnace.updateEntityServer`, jar
2.8.195): каждый тик, если печь горячая и рецепт подошёл —

```
if (fluid <= fluidTank.getFluidAmount()) { progress += 1; fluidTank.drainInternal(fluid, true); }
if (progress >= duration) { operateOnce(...); progress = 0; }
```

То есть **суммарный расход = fluid × duration**. У стали
(`@fluid:1 @duration:6000`) это 6 000 мБ и 5 минут при баке 8 000 мБ.

**Последствие.** Наши `fluid = 2, duration = 12 000` дали бы **24 000 мБ**
на слиток — вчетверо против стали и три полных бака за один слиток, при
том что задумывалось «вдвое дороже».

**Исправлено в карточке:** `duration = 12 000`, `fluid = 1`. Удвоенная
длительность **сама** удваивает расход воздуха — ровно то, что и хотели.

**Побочно вскрылось:** путь А — это 10 минут на слиток, а комплект брони
требует 24 слитка, то есть четыре часа работы печи. Записано в карточку
как открытый вопрос: «магический» путь оказался длинным, «технический»
(тигель) — коротким, и выбор может выродиться в один вариант.

## А-3 (важно, T3). Резервуар Эссенции хранит 256 **смеси**, а не одного аспекта

**Суть.** Вся сверка «мы не должны превзойти пустотный контейнер»
(`essentia_logistics.md` §4) строилась на том, что резервуар держит
256 **одного** аспекта. Это неверно.

**Доказательство** (`TileEssentiaReservoir`):

```java
public int maxAmount = 256;
public AspectList essentia;                       // не (aspect, amount), а список!
doesContainerAccept(tag)  → containerContains(null) < maxAmount   // любой аспект
addToContainer(tag, amt)  → add = min(amt, maxAmount - containerContains(null))
```

Сравнить с банкой (`TileJarFillable`): там именно одно поле `aspect` и
`amount` с потолком 64 — вот это «64 одного аспекта».

**Последствие.** «Много разных аспектов в одной точке» — **не наша
уникальная ниша**, резервуар это уже умеет. И требование владельца «хуже
или дороже пустотного контейнера» по одному параметру нарушено: у нашего
накопителя 512 суммарно против 256.

**Что сделано:** факты в §4 исправлены, сравнительная таблица переписана,
поставлен явный вопрос владельцу — срезать накопитель до 256 суммарно
(рекомендуется) или оставить 512, оправдав ценой и питанием.

## А-4 (важно, T1). Аспекты трёх солнечных шлемов ASP уходят в никуда

**Суть.** `ASPAspects` регистрировал аспекты по именам
`advanced_solar_helmet`, `hybrid_solar_helmet`, `ultimate_solar_helmet`.

**Доказательство** (исходники ASP,
`items/ItemArmourSolarHelmet.java`):

```java
BlocksItems.registerItem(this, new ResourceLocation("advanced_solar_panels", type.getName()));
// SolarHelmetTypes.getName(): return this.name + "SolarHelmet";  // lowerCamelCase!
```

Реальные registry-имена — `advancedSolarHelmet`, `hybridSolarHelmet`,
`ultimateSolarHelmet`. Snake_case встречается только в путях **моделей**
(`CaseFormat.LOWER_CAMEL.to(LOWER_UNDERSCORE, …)`) — на этом и легко
обмануться. Предмет `crafting` (метки 0…13) назван верно.

**Последствие.** Три шлема оставались без аспектов: не сканируются, не
дают очков исследования, в тигле бесполезны. В лог при этом падало по
WARN на каждый (`ModItems.item`), но их никто не читал.

**Исправлено** в сабмоде 0.2.2.

## А-5 (важно, T1). Семь из восьми рецептов дробилки требуют Шёлкового касания

**Суть.** Мы обещаем «дробление руд ТК ×2» как первую пользу техники для
мага. Но большинство руд ТК **не выпадают блоком**.

**Доказательство** (`BlockCustomOre.getDrops`):

| Мета | Руда | Что падает |
|---|---|---|
| 0 | киноварь | **сам блок** ✔ дробится |
| 1–6 | зачарованные (6 стихий) | `itemShard` ×(1 + rand(1+fortune)) — блока нет |
| 7 | янтарная | `itemResource:6` (янтарь) ×(1 + rand(1+fortune)) — блока нет |
| 8 | серебряная (наша) | **сам блок** ✔ (ветка `else`) |

То есть из восьми рецептов дробилки без Шёлкового касания работает
**один** — киноварь (плюс серебро, которое теперь обрабатывает сам IC2).

**Последствие.** Обещание T1 «маг дробит свои руды ×2» выполняется только
для игрока с Шёлковым касанием. Хуже: с Фортуной III прямой дроп даёт до
четырёх осколков, то есть дробилка (фиксированные 2) может быть **хуже**
обычной кирки.

**Предложение.** Не выдавать это за флагман T1: переписать формулировку в
`03_progression.md` §5 и на странице исследования — «Шёлковое касание +
дробилка = стабильные 2 без удачи», а не «×2 руды». Либо поднять выход
зачарованных руд до 3 осколков, чтобы дробилка выигрывала у Фортуны.

## Опровергнуто (чтобы вопрос не поднимался снова)

**«Таум-Оверклокер не сможет менять множители на лету: `onTick → true`
ничего не пересчитывает».** Проверено по байткоду 2.8.195 — цепочка
работает целиком:

```
TileEntityStandardMachine.updateEntityServer
  → upgradeSlot.tickNoMark()            // зовёт IUpgradeItem.onTick для каждого стека
  → если вернул true: markDirty()
TileEntityStandardMachine.markDirty()   // ПЕРЕОПРЕДЕЛЁН
  → setOverclockRates()
      → upgradeSlot.onChanged()          // resetRates(): перечитывает множители
      → пересчитывает operationLength и energyConsume машины
```

Карточка `05_objects/thaumic_overclocker.md` §4.2 описывает это верно,
менять ничего не нужно.

## Третья волна: аспектная экономика (проверено вручную)

### А-12 (БЛОКЕР, канон+код). Формула не воспроизводила ни одного числа из карточек

Поскольку по решению владельца аспекты теперь **регистрируются явно по
формуле**, §7 карточек — это спецификация для кода. Проверка показала,
что спецификация была невыполнима сразу по четырём причинам:

1. **Неверные исходные данные.** `tempered_thaumium.md` считал от «таумий
   = `Metallum 8, Praecantatio 8`». Явной регистрации у `itemResource:2`
   в порте нет: ТК выводит аспекты из тигельного рецепта —
   железо (`Metallum 4`) + `sqrt(Praecantatio 4)` = **`Metallum 4,
   Praecantatio 2`**. Вдвое-вчетверо меньше.
2. **Порог убивал простые предметы.** Нижняя граница `max(2, 15 %)` при
   двух-трёх компонентах превращалась в «отсечь всё, что меньше двух»:
   у слитка исчезал **весь** `Praecantatio` (при том что весь лор
   материала — «фиолетовые вкрапления»), а у лопаты (слиток + две палки,
   все аспекты по 1) не оставалось вообще ничего. Граница снижена до 1;
   разобранный пример канона §3 при этом не изменился — там фильтрует
   процент (15 % от 18 = 2.7), а не абсолютный минимум.
3. **Подпись процесса накапливалась по цепочке.** Слиток получал от домны
   `Ignis +3`; броня из восьми слитков — уже `Ignis 14`, и «огонь»
   становился главным аспектом стального доспеха. Введено правило §2.4а:
   подпись зажимается сильнейшим материальным аспектом.
4. **Карточки применяли несуществующие подписи и выдумывали аспекты.**
   `tempered_thaumium_armor.md` и `thaumium_wrench.md` использовали
   подпись **арканного** верстака на предметах, которые куются на обычном
   (строки таблицы для обычного верстака в каноне не было вовсе), и
   дописывали `Tutamen` / `Instrumentum` руками. Это двойной счёт:
   `ThaumcraftCraftingManager.getBonusTags` добавляет их **сам** — броне
   `Tutamen` по `damageReduceAmount`, мечу `Telum` по урону, кирке
   `Perfodio` по материалу.

**Что сделано.** В канон добавлены §2.4 (строка «обычный верстак —
подписи нет»), §2.4а (потолок подписи) и §2.6 (назначение предмета
приписывает ТК, руками не пишем); порог снижен до 1; в коде
`AspectFormula` обе правки внесены. Пересчитаны и записаны точные числа:

| Объект | Итог формулы |
|---|---|
| Слиток закалённого таумия | `Metallum 2, Ignis 2, Praecantatio 1` |
| Нагрудник (8 слитков) | `Metallum 10, Ignis 10, Praecantatio 5` |
| Поножи (7) / шлем (5) / ботинки (4) | `8/8/4` · `6/6/3` · `5/5/2` |
| Таумиевый ключ (6 слитков) | `Metallum 7, Ignis 7, Praecantatio 4` |
| Кирка, топор (3 слитка + 2 палки) | `Metallum 4, Ignis 4, Praecantatio 2, Arbor 1` |
| Меч (2 + 1) | `Metallum 2, Ignis 2, Praecantatio 1, Arbor 1` |

У остальных карточек §7 честно помечен как **профиль, а не расчёт**:
их компоненты — предметы IC2, чьи аспекты берутся у движка в рантайме,
и точный итог даёт строка `Aspect formula <объект>:` в логе.

### А-17 (мелко, T4). Числа наконечников жезлов из архива хуже ванильных

Поле `WandCap` — **множитель** стоимости (`ItemWandCasting` §217/§246), а
не «скидка в процентах». Реестр порта: iron 1.1, gold 1.0, thaumium 0.9,
void 0.8, ichor 0.8. Архивные «5 %» и «15 %» дают 0.95 и 0.85, то есть
таум-стальной наконечник **хуже таумиевого**, а иридиевый (T4) — **хуже
пустотного** (мид-гейм). Со скипетром разрыв ещё больше (−0.1 сверху).

**Требование на будущее:** иридиевому наконечнику нужен множитель **≤ 0.75**
(скидка ≥ 25 %), таум-стальному — **≤ 0.88**. Стержни при этом в порядке:
150 против лучшего ванильного `silverwood` 100 — находка ошибалась.

### Девять дефектов кода сабмода (первый прогон этого среза)

1. **Гвард-тест канона был сломан переименованием** — 3 из 4 тестов падали,
   защита курсов не работала.
2. **Свет Эфирного Двигателя 5 вместо 7** — парные машины светили по-разному.
3. **Ни один тайл не звал `markDirty`** — буфер EU мог не сохраниться:
   `Chunk.needsSaving` требует `isModified`, а машина, копящая EU в пустой
   комнате, чанк не пачкает.
4. **Кэш узлов пересканировался вечно** (4913 позиций каждые 100 тиков):
   `markStale()` звался на каждую неудачную попытку, а неудача — штатный
   режим (реген узла 1 вис/600 тиков против попытки раз в 20).
5. **`ACTIVE` мигал 20 тиков из 600** — означал «забрал вис сейчас», а не
   «работает»; каждое переключение тянуло пересчёт освещения и пакет.
6. **Машина ломалась деревянной киркой** — `setHarvestLevel` не вызывался.
7. **Курс дороже буфера убивал генератор молча** — добавлено предупреждение.
8. **Формула могла выдать 6–7 аспектов** вопреки §2.3: обрезка до пяти шла
   до подписи, а арканный верстак и инфузия дают по два аспекта.
9. **Возможна была нулевая запись** `{Machina: 0}` при пустых материалах.
